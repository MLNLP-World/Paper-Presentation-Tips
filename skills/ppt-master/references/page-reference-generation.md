# 单页设计简报与 AI 整页参考图

在内容框架已确定、准备生成参考图时读取。本文件适用于 Default、Quick 和重新设计/美化页面；用户提供的已确认页面图片可直接作为复刻依据。它不改变聊天批准门或最终原生 PPTX 的要求。

生成新参考页前，先完成 [缺陷识别与用户确认](pre-reference-diagnosis.md)，据确认结果完善逐页内容和结构，再执行本文件。已经批准内容框架不代替该确认；已指定最终图片的严格复刻按该规范的适用范围保留原貌。

## 1. 默认走实际的整页 AI 生图

**默认使用当前 agent 的内置图像生成/编辑工具，生成含完整内容的逐页参考图。** 标题、正文、图注、数据标签、图表和示意图都可以出现在 AI 参考图中。不要因这些内容最终需要可编辑，就禁止它们出现在参考图中，或只让 AI 画无字背景。

这是两项独立决策：

| 决策 | 所属阶段 | 含义 |
|---|---|---|
| `reference_generation: host_native_image` | 页面设计 | 内置 AI 工具构思并生成完整参考页面 |
| `reference_generation: external_image_api` | 页面设计 | 用户选定的外部 API 生成完整参考页，保留 provider/model、调用来源和选择记录 |
| `image_usage`、`Acquire Via`、`AI Image Acquisition Path` | 最终资源 | PPTX 是否需要独立位图素材及其来源 |

**最终素材没有 AI 图片，不代表参考图不能由 AI 生成。** 即使最终所有文字、图表和流程都原生可编辑，仍默认先调用 AI 生成整页参考图。不能用 `image_usage: none` 或最终素材的 `AI Image Acquisition Path: not applicable` 跳过该步骤。不要把参考图冒充最终放映页。

SVG/Canvas/HTML → PNG 是程序设计参考图，不是 AI 生图。仅当用户明确选择这种方式、指定必须精确复用的模板，或工具缺失后用户选择该替代时采用；如实记录实际方法。不得为了省事、保证可编辑或避免核对 AI 文字而静默替换。宿主没有绘图能力时，先列具体阻塞，继续独立内容准备，由用户选择已配置的 API、提供参考图或原生替代。API 调用必须显式选择，且如实记录来源。

### 没有内置生图工具时

可使用用户选定并配置的 API。调用 `scripts/image_gen.py` 时加 `--allow-api`；需要背景或风格参考时，核实后端支持图片编辑，并用单页 `--reference-image` 实际传入图片。完整提示词、源材料和聊天确认流程相同。

API 页的 `generation.method` 写 `external_image_api`，并记录真实 `tool`、`invocation_ref`、`prompt`、`provider`、`model` 和 `authorization.message/message_id`；`references` 继续绑定实际图片。不要记录密钥，也不要把 API 图片标成宿主内置生图。

## 2. 把结构规划转成可画的单页简报

先落实 [规划阶段的模板与资源参考](academic-chat-design.md#1a-规划阶段先参考现有模板与资源)。在方案阶段实际查看适合的规范、样页与视觉资源，说明拟用在哪些页、借鉴什么；不要等画图时才发现资源。`design_spec.md` 保留整套规划与来源，不直接当图像提示词。先为每页写 `reference_review/briefs/P01.md`，内容精炼但具体：

1. **本页只回答什么**：一句问题和一句听众应带走的结论。
2. **真正上屏的文字**：确切标题、短句、图注、数据标签；与讲解意图区分。需要逐字保留的内容标清。
3. **主图究竟画什么**：明确实体、数量、动作和关系，例如“四根比较柱”“两个相似回答经过校准”“同一上下文在条件绑定处形成两条轨迹”，不能只写“配示意图”“展示研究框架”。
4. **数据或机制依据**：图表提供类别、原始数值、单位、条件与轴含义；流程给真实输入、处理、变化和输出。来源完整记录在简报，画面只放必要的短来源。
5. **视觉主次与取舍**：先看哪里、主比较如何突出、右侧最多保留哪些短句、哪些解释放讲稿。承接 [通用视觉约定与配色用途](academic-chat-design.md#1c-通用视觉约定与配色用途)，写明本页“组件/语义 → 色系”的对应关系及保留原色的范围；同类结构不机械分色，表头与重点数据区作为整体配色。不要把核心结论在标题、大数字卡和正文重复三遍。
6. **实际参考图片及用途**：背景、视觉风格、内容原图分别列真实文件路径及作用，不能只写一个 PPT 名称。
7. **参考资源与采用方式**：承接规划中选定的 Style/Brand 规范、Layout/Deck 样页、图表/表格或图标，写实际查看文件、具体借鉴点与允许变化处。无合适资源时说明按内容自由设计即可。视觉样页用于生图时准备并传入真实 PNG；文字规范提炼为明确设计要求，不能用一个路径代替。

按页面任务决定主图：实验页做有依据的比较；机制页让图形表达输入/变化/输出；动机页先给案例。不要把每页都变成相同卡片、图标或流程框。描述重点与关系，给图像模型设计空间；此时不锁死逐对象坐标、SVG 节点、原生组件类型、所有字号或可编辑实现方案。

讲解意图不是上屏文字。例如“这里顺便解释两个模块关系”供模型组织视觉，不能原样印在页上；没有科学依据的机制解释也不能作为已证实结论进入画面。

## 3. 写能直接交给工具的完整提示词

将简报整理为 `reference_review/prompts/P01.md`。使用自然、具体的单页设计语言；不把整套规格、对象 JSON、12 条检查表或论文全文粘进去。允许小标题、列表和数据表，**不受资源插画的单段/150–300 词模板限制**。不使用“精美、高级、现代”代替具体的主体、阅读路径和重点。

推荐形状（按内容调整，不强制逐项念给用户）：

```markdown
请使用所附参考图片，按已确认的[画布比例与尺寸]设计一张完整的中文学术汇报 PPT 参考图。
这页只解释：[一个问题]。希望观众记住：[一句结论]。

页面标题：[准确的上屏标题]。
主体画：[明确的实体/动作/图表及阅读顺序]。
[需要的数据表、条件、单位、图形语义，或具体示例输入输出]。

视觉重点：[哪个对象/方法/变化最突出；同类组件统一使用什么色系，哪些独立内容或数据类别需要分色，以及表头与重点区如何协调]。
旁边只写：[具体短句]。
不必上屏、仅帮助你理解的意图：[讲解思路]。

参考图1用于[背景/风格/原图插入]；参考图2用于[...]。
延续背景与视觉语言，文字大而协调，主图充分展开，避免空旷失衡或重复数字卡。
请生成整页完整内容，不只生成背景，也不要把这些绘图说明印在页面上。
```

### 示例：消融比较页

以下数字仅来自用户给出的示例，不作为其他项目的固定答案：

> 请根据所附背景，生成一张完整学术汇报页面。标题是“两个 Calibration 都有贡献，组合效果最好”。主体用四根柱比较同一设置下的 LC Win Rate：SPPO 44.79、仅 Supervision Calibration 46.16、仅 Representation Calibration 45.20、Both 47.46。标清指标、数值与实验条件；不要添加不存在的误差条。
>
> SPPO 用灰色；两个单模块用协调的浅色；Both 用主色深蓝突出。主图占主要阅读空间，右侧只写“监督校准单独贡献更大”和“双重校准效果最好”。希望听众看清单模块与组合的关系，不逐项复述实现细节。沿用参考背景和学术风格，让正文、图注和数值足够大。请生成完整页面，绘图说明不要出现在图中。

## 4. 真正传入参考图片

- **背景图片**：作为背景/编辑目标传入，按用户要求保留其主体与留白区域；不能仅凭文字重述大致颜色。
- **风格样页**：从实际 PPTX 渲染或用户附件中选能代表风格的少量页面，先查看，再作为视觉参考传入。吸收配色、字重、疏密与示意方式，不能抄进样页里的文字、数据或论文结论。
- **论文原图**：作为内容资产保留，不能让生成模型重画一个相似但错误的证据图。必要时在 AI 构图基础上保留/插入精确原图或数据图，并如实注明混合制作；不能因此将整页退回统一 SVG 模板。

具体 API 字段服从宿主工具文档。例如 Codex 使用可调用的 image generation/editing 工具；本地图片先查看，按工具支持的参考图片参数传入。不要假设每种 agent 都有图像工具，也不要把文件名当作已经传入图片。

工具返回后，将实际图像保存到项目目录。记录真实工具调用来源，不能把 SVG 渲染或脚本生成的图谎称为模型输出。工具返回的默认保存位置不等于交付位置；不能编造路径。

## 5. 目视核对、记录并等待确认

先检查完整画面：核心任务能否一眼识别，主图是否具体且有含义，主次、整体观感、字体和背景是否协调。再核对标题、中文、数值、类别、标签、尺度、公式及条件。必要时放大局部。不能因为“是参考图”就接受错字、假数据或图文矛盾，也不要用精确坐标检查代替整体观感。

图像中的数据只是设计呈现，事实仍来自源表/原文，不能反向从生成图提取成实验数据。若模型画错，按错误做定向编辑/重试；同一问题两次有针对性的修复仍不可靠，说明具体问题，并向用户提出原图/精确数据图局部保留或其他选择。不静默改成整页程序图。

为新的页清单写明方法，独立于最终资源清单：

```json
{
  "reference_generation": "host_native_image",
  "bindings": ["sources/content.md"],
  "pages": [{
    "id": "P01", "svg": "slide_01.svg",
    "reference": "reference_review/P01-r1.png",
    "blueprint": "reference_review/P01.json",
    "generation": {
      "method": "host_native_image", "tool": "<实际内置工具名>",
      "invocation_ref": "<真实工具调用来源>",
      "prompt": "reference_review/prompts/P01.md",
      "references": [{"path": "sources/style-page.png", "role": "style"}]
    }
  }]
}
```

可选参考图角色为 `background`、`style`、`content_asset`；无参考图时 `references: []`。如果用户选择程序设计参考，`method: native_design` 并记录 `authorization.message` 和 `authorization.message_id`；用户选定已有完整页面用 `provided_frame`。这些字段是可追踪的声明，脚本不能认证工具调用或人类身份。

`reference_review.py prepare` 会绑定提示词、参考图片、实际输出及内容蓝图的哈希；改变其一会使相关批准失效。旧 v1 项目仍可读取，但不能把旧的未记录方法 PNG 自动标成 AI 图。需要重新出图的页面按本流程记录新方法。

完成检查后，在聊天展示实际整页图片、页号和版本，等待明确回复。框架确认、用户要求使用 AI、工具执行成功均不等于用户已批准新图。不得为了通过门禁伪造批准。

## 6. 批准后才落实组件与坐标

参考图批准前的蓝图只承载内容、来源和视觉意图，不要求 `positioned_scene`。批准后，将构图拆为原生文字/段落/run、图表与数据、形状/连接线、公式、独立图片，在 `reference_review/native_maps/P01.json` 等**单独的派生文件**记录坐标、字号、图层和对象映射，并绑定批准图的哈希。不要为了加入这些实现参数而改写已经冻结的内容蓝图、反复要求用户确认。

保持完整参考图的设计进行原生复刻，不使用整页截图加少量文本框。照片/背景/复杂原图可保留独立图片。最终仍需重新读取并渲染实际 PPTX，与参考图逐页核对。参考图阶段允许完整 AI 文字与图表，不意味着最终允许放弃可编辑性或数据验证。
